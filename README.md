# liranapp — חילוץ שדות מטופסי הצעה לביטוח

מערכת שמקבלת טופס הצעה לביטוח (PDF), מזהה את השדות שמולאו בו, ומחזירה
מיפוי מובנה `שם שדה → ערך` עם רמת ביטחון ומיקום מקור לכל שדה — יחד עם
מסך פשוט להצגת התוצאות.

**שלב נוכחי: שלב 1 — זיהוי שדות שמולאו בלבד.** שלב 2 (זיהוי שדות ריקים,
באמצעות השוואה לרשימת כל שדות התבנית) עדיין לא מומש, אך הארכיטקטורה בנויה
כך שניתן להוסיף אותו בקלות (ראו "הרחבה לשלב 2" למטה).

## הרצה מקומית

### אופציה א׳: Docker (מומלץ — לא דורש התקנת Python/poppler ידנית)

דרישה יחידה: [Docker](https://docs.docker.com/get-docker/) מותקן ורץ.

```bash
docker compose up --build
```

גשו ל-`http://localhost:8000`.

### אופציה ב׳: הרצה ישירה עם Python

```bash
# תלות מערכת: poppler-utils (מספק את pdftotext)
apt-get install -y poppler-utils   # macOS: brew install poppler

cd backend
python3 -m venv venv && source venv/bin/activate
pip install -r requirements.txt
uvicorn app.main:app --reload --port 8000
```

גשו ל-`http://localhost:8000` — ה-API (`/api/analyze`) וה-UI הסטטי
(`frontend/index.html`) מוגשים יחד מאותו שרת.

בדיקות (רצות תמיד; הבדיקה מול מסמך אמיתי מדלגת אם לא הוגדר משתנה סביבה):

```bash
INSURANCE_FORM_SAMPLE_PDF=/path/to/local/sample.pdf pytest tests/
```

> **הערה על נתונים אישיים:** מסמכי הצעה לביטוח מכילים מידע אישי רגיש
> (ת"ז, טלפון, כתובת, הצהרות בריאות, חתימות). אף קובץ PDF לדוגמה אינו
> נשמר במאגר הקוד (ראו `.gitignore`).

## מה נותח במסמך המקור

המסמך שסופק לצורך הפיתוח נבדק לעומק לפני כתיבת קוד:

- **PDF טקסטואלי, לא סרוק.** `pdftotext` מחלץ טקסט ישירות ובאיכות מלאה —
  אין צורך ב-OCR (ראו סעיף OCR למטה למקרה שבו יידרש).
- **מוצפן (AES-256) אך פתוח לקריאה** — הצפנה ברמת ההרשאות בלבד (חתימה
  דיגיטלית/מניעת עריכה), לא סיסמת פתיחה. `pdftotext` פותח אותו ללא בעיה.
- **ללא שדות PDF אינטראקטיביים (AcroForm).** יש רק שדה `/Sig` אחד (חתימה
  דיגיטלית). כל שאר התוכן — כולל הערכים שמולאו — הוא טקסט/גרפיקה
  "שטוחים" על העמוד, לא Widgets. המשמעות: אי אפשר לקרוא `/V` מתוך שדה
  טופס; יש להבין את המבנה החזותי.
- **סימוני ✔ הם טקסט אמיתי**, לא תמונה. הם מגיעים מגופן Symbol
  (ZapfDingbats) עם מיפוי glyph→Unicode לא סטנדרטי — `pdftotext` פותר
  זאת נכון, בעוד ספריות Python כמו PyMuPDF/pypdf לא בהכרח (ראו "בחירות
  טכניות" למטה).
- **שני מוסכמות מרחביות חוזרות** לאורך כל המסמך:
  1. **טבלת פרטים** (שם/ת"ז/תאריך לידה/כתובת וכו') — הערך מודפס **מעל**
     התווית שלו, באותה עמודה אנכית.
  2. **שאלת כן/לא או בחירה** — סימון ✔ צמוד לצד הימני (תחילת קריאה
     ב-RTL) של האפשרות שנבחרה.
- **טקסט עברי בפלט `pdftotext -bbox-layout`** מגיע בסדר תווים הפוך
  (ויזואלי, לא לוגי) ועם ניקוד "רעש" שנדבק מקידוד הגופן (לדוגמה ל' הופכת
  ל-"ֹל"). זה מתוקן ב-`text_normalize.py` (הפיכת סדר תווים + הסרת ניקוד).
- מבנה חוזר על עצמו: 2 "מועמדים לביטוח" עם אותם שדות בדיוק, טבלת מוטבים
  x2 (ריקה במסמך הבדיקה), 13 קטגוריות בהצהרת בריאות x2 מועמדים (כן/לא),
  טבלת "רשימת החתמות" אמיתית עם כותרות עמודה וכמה שורות נתונים.
- טקסט סטטי (כותרות, הסברים משפטיים, פסקאות תנאים) מובחן מערכים שמולאו
  לפי גיאומטריה (רוחב/מרחק/יישור עמודות) ולא לפי תוכן — ראו "כיצד
  מבדילים בין תווית לערך" למטה.

## ארכיטקטורה

```
PDF
 ↓
pdf_extraction/bbox_extractor.py   (pdftotext -bbox-layout → Word/Line לפי עמוד)
 ↓
pdf_extraction/text_normalize.py   (תיקון RTL + ניקוד רעש)
 ↓
template/shlomo_life_insurance.py  (הגדרת שדות התבנית — FieldSpec/TableSpec)
 ↓
extraction/patterns.py + tables.py (איתור ערך לפי תבנית: grid / checkbox / table)
 ↓
extraction/confidence.py           (ציון ביטחון לפי איכות ההתאמה הגאומטרית)
 ↓
extraction/engine.py               (תזמור + טיפול ב-PDF סרוק + סיכום)
 ↓
JSON מובנה (FieldResult / ExtractionResult)
 ↓
main.py (FastAPI: POST /api/analyze)  +  frontend/index.html (טבלה + סיכום)
```

הפרדה ברורה: **Parsing** (`pdf_extraction/`) לא יודע כלום על טפסי ביטוח;
**Template** (`template/`) הוא הידע היחיד על המבנה הספציפי של הטופס הזה,
כדאטה בלבד (בלי קוד); **Extraction** (`extraction/`) מיישם את חוקי החיפוש
הכלליים (grid / checkbox / table) בלי לדעת אילו שדות ספציפיים קיימים;
**API/UI** לא נוגעים בלוגיקת החילוץ בכלל.

### כיצד מבדילים בין תווית לערך (ולא מנחשים)

- **Grid** (`patterns.py::extract_grid_field`): מאתרים שורת טקסט שהיא
  התאמה מדויקת לתווית ידועה (`anchor_text`), ואז מחפשים את שורת הטקסט
  **הקרובה ביותר מעליה** (או מתחתיה, לשדות בודדים כמו כותרות) שגם
  מיושרת אנכית עמה (IoU של טווחי ה-X) וגם ברוחב סביר (לא פסקת הסבר
  שמזדמן לחפוף לטווח ה-X של תווית צרה). אם אין התאמה כזו בתוך מרחק
  מקסימלי — השדה **לא מוחזר בכלל** (לא ריק, לא מנוחש).
- **Checkbox / בחירה** (`patterns.py::extract_choice_field`): מאתרים את
  מילת ה-✔ ובודקים איזו מילת-אפשרות יושבת צמוד אליה (המרחק האופקי
  הקטן ביותר, בכיוון קריאה נכון). אם יש כמה "מועמדים" (שני אנשים באותה
  שורה) — מפרידים לפי טור ימין/שמאל.
- **טבלה** (`tables.py::extract_table`): גבולות העמודות נגזרים ממיקום
  כותרות העמודה עצמן (לא קואורדינטות קבועות), כדי שהמנגנון יעבוד גם אם
  הטבלה זזה אנכית במסמך אחר. תאים שהם בסך הכל חזרה על כותרת/מספר
  שורה/סימון מגדר לא-מסומן (שאריות של שורה ריקה בטבלה) מסוננים.

### חישוב Confidence

אין "ניחוש" של רמת ביטחון — היא נגזרת ישירות מאיכות ההתאמה הגאומטרית:

| טווח | משמעות | מבוסס על |
|---|---|---|
| 0.95–0.99 | כמעט ודאי | חפיפת עמודות מלאה, מרחק אנכי מזערי |
| 0.80–0.94 | טוב | חפיפה/מרחק סבירים אך לא מושלמים |
| 0.60–0.79 | לבדיקה | התאמה חלשה — מוצג אך מסומן `needs_review` |
| מתחת ל-0.60 | — | **לא מוחזר כלל** (עדיף "לא בטוח" מאשר שיוך שגוי) |

מדדים: `x_overlap_fraction` (IoU של טווחי ה-X בין תווית לערך), המרחק
האנכי בין השורות, ובבחירות — המרחק האופקי בין ה-✔ לאפשרות שנבחרה.

### מקור לכל שדה (Debug)

כל `FieldResult` כולל `source`: סוג ההתאמה (`text_grid`/`checkbox`/
`table_cell`), הטקסט הגולמי שנמצא, תווית העוגן (`anchor_label`), ותיבות
התיחום (bbox) של הערך והעוגן — כדי שאפשר יהיה לדבג בעתיד למה שדה מסוים
שויך לערך מסוים.

### הרחבה לשלב 2 (טרם מומש)

`template/schema.py::FieldSpec` ו-`FieldResult.status` כבר בנויים כך
שהרחבה לזיהוי שדות ריקים היא תוספת, לא שינוי מבני:

```json
{"field_name": "מצב משפחתי", "status": "empty", "value": null}
```

כדי לממש: להריץ את מנגנון איתור העוגנים (`_find_anchor_lines`) על *כל*
`FieldSpec` בתבנית (לא רק אלה שהניבו תוצאה), ולסמן `status="empty"` לכל
עוגן שנמצא אך בלי ערך תואם לידו. אין צורך בשינוי בפורמט הנתונים או
ב-API — רק בלולאה נוספת ב-`engine.py`.

## טיפול ב-PDF סרוק (OCR)

המסמך שנבדק לא היה סרוק, כך שלא מומש OCR בפועל. `engine.py` בודק יחס
מילים-לעמוד שחולצו על ידי `pdftotext`, ואם הוא נמוך מדי — מחזיר אזהרה
מפורשת ("המסמך נראה כמו PDF סרוק... נדרש OCR") במקום לנחש תוכן ריק.
אם וכאשר יידרש OCR אמיתי בעתיד, הגישה המומלצת:

- **Tesseract OCR** עם חבילת השפה העברית (`tesseract-ocr-heb`), ברמת
  `--psm` שמתאימה לטופס (לרוב `6`, בלוק טקסט אחיד), **לא** ניחוש גנרי.
- לשמור bounding boxes ברמת מילה (Tesseract TSV output) כדי להזין את
  אותו `Word`/`Line` model הקיים — כך שכל שכבת ה-`patterns.py` תעבוד ללא
  שינוי, בין אם המקור הוא `pdftotext` או OCR.
- לשמר `page_number` מקורי (rendering לפי עמוד, לא מסמך שלם כתמונה
  אחת).
- RTL בעברית: Tesseract עצמו לא עושה reshaping/bidi של ערבית-עברית
  כמו שצריך תמיד נכון — יש לוודא עם `--oem`/גרסת tesseract מספיק
  חדשה, ולהפעיל את אותו תיקון `text_normalize.py` על הפלט.
- Checkbox בסריקה: סימון ✔/X הוא גרפי (לא טקסט) בסריקה — יידרש זיהוי
  תבניות ויזואלי נפרד (למשל: זיהוי כתמי פיקסלים כהים בתוך תיבת ✔
  ידועה-מראש מהתבנית) ולא זיהוי OCR טקסטואלי.
